# Software Supply-Chain Security
Why Are Supply-Chain Attacks Hard to Detect? | Intermediate | Dependency Risk | A compromised dependency can execute with the same trust as your own code, often through a legitimate update. There is no obvious payload at review time. | Most organizations trust far more code than they can inspect. | How would you detect that a routine dependency update started exfiltrating data? | supply-chain, detection, dependencies
How Does Build Provenance Help Verify Software? | Advanced | Build Provenance | Provenance records what source, builder, and inputs produced an artifact, signed so consumers can verify it was built as claimed. | It closes the gap between source review and the binary actually shipped. | What evidence does a verifier need to trust a build provenance attestation? | provenance, signing, builds
What Makes a Dependency Confusion Attack Possible? | Intermediate | Registry Security | Package managers may resolve names from public and private registries. An attacker publishes a public package with the same name and a higher version, hijacking installs. | Internal package names are an attack surface when registries are mixed. | How would you scope package resolution so private names cannot be shadowed? | dependency-confusion, registries, packages
Why Is a Lockfile a Security Control? | Beginner | Dependency Risk | A lockfile pins exact resolved versions and integrity hashes, preventing silent upgrades to a compromised or incompatible release. | Reproducible installs reduce the window for unexpected dependency changes. | What does an integrity hash in a lockfile actually protect against? | lockfiles, pinning, reproducibility
How Do SBOMs Help Incident Response? | Intermediate | SBOMs | A software bill of materials lists components and versions, allowing teams to search for a vulnerable package across many products when an advisory lands. | When a new CVE appears, response speed depends on knowing what you ship. | What makes an SBOM useful beyond a raw dependency list? | sbom, incident-response, inventory
What Makes Package Signing Useful but Insufficient? | Advanced | Signing | Signatures verify who published a package and that it was not modified, but they do not prove the publisher's intent, the code's safety, or the build's integrity. | Trusting a maintainer's key is not the same as trusting every future release. | What additional controls are needed after verifying a package signature? | signing, trust, packages
Why Are Abandoned Packages a Security Risk? | Beginner | Dependency Risk | Unmaintained packages stop receiving fixes and may be taken over through account recovery or transferred ownership, allowing malicious releases. | Dependencies can change owners without changing names. | How would you monitor a dependency for signs of abandonment or takeover? | abandoned, takeover, maintenance
How Do Reproducible Builds Enable Trust? | Advanced | Build Provenance | Reproducible builds let independent parties rebuild source and compare hashes, detecting tampering in the build environment or distribution path. | They turn shipping binaries into a verifiable claim rather than an act of faith. | What inputs must be eliminated for two independent builds to match? | reproducible-builds, verification, trust
What Makes a Typosquatting Attack Effective? | Beginner | Registry Security | Slightly misspelled package names attract installs from developers who trust autocomplete or memory. Malicious packages then execute during installation. | The attack exploits human attention, not cryptographic weakness. | How could a tool detect a suspiciously similar package name before install? | typosquatting, packages, human-error
