# API Design & Integration
How Do Engineers Design Backward-Compatible APIs? | Intermediate | Versioning | Compatibility means old clients keep working after new fields, endpoints, and behaviors are added. Additive changes are usually safe; renames, removals, and stricter validation are not. | APIs are promises, and breaking them breaks every integration simultaneously. | Which schema change would be safe for a client that ignores unknown fields? | api-design, compatibility, evolution
What Makes API Versioning Painful? | Intermediate | Versioning | Versions multiply maintenance, documentation, and test matrices. Choosing between URL versions, headers, and additive evolution determines how long old clients linger. | The cost of a versioning scheme appears years after the initial design decision. | When does adding an optional field avoid the need for a new version? | versioning, evolution, maintenance
Why Is gRPC Often Faster Than JSON over HTTP? | Intermediate | RPC vs REST | gRPC uses compact binary encoding, HTTP/2 multiplexing, and generated clients, reducing payload size and allowing concurrent streams on one connection. | The performance difference depends on the workload, not just the protocol label. | Which part of gRPC's advantage disappears for large binary payloads? | grpc, protobuf, protocols
What Makes an Idempotency Key Work? | Intermediate | API Contracts | A client-generated key lets the server recognize retries of the same request and return the original result instead of repeating side effects. Storage and scope must be well defined. | Payment and order APIs rely on this pattern to prevent duplicate charges. | How long must an idempotency key be retained, and what happens after expiry? | idempotency, retries, payments
How Should APIs Communicate Partial Failure? | Advanced | API Contracts | A batch operation may succeed for some items and fail for others. The response must preserve per-item outcomes without pretending the whole request failed or succeeded. | Clients cannot recover correctly from a misleading aggregate status. | What response shape would let a client retry only the failed items? | partial-failure, batch-apis, errors
Why Does Pagination Need a Stable Cursor? | Intermediate | API Contracts | Offset pagination shifts when items are inserted or deleted. Cursors encode a position in a stable order, reducing duplicates and skipped records during iteration. | Feeds and exports behave incorrectly under concurrent writes when offsets are used. | What does a cursor need to encode to survive new rows being inserted? | pagination, cursors, consistency
What Makes a Webhook Signature Useful? | Beginner | API Contracts | A signature proves a payload came from the sender and was not modified, provided the receiver verifies it against a shared secret and checks freshness. | Unsigned webhooks let attackers forge events that trigger real side effects. | Why does a signature need a timestamp or replay protection to be trustworthy? | webhooks, signatures, security
How Do API Gateways Change System Design? | Intermediate | Integration Patterns | Gateways centralize authentication, routing, rate limiting, and transformation, reducing duplication but adding a shared component whose failure affects every service. | A gateway is both a consistency win and a single point of operational risk. | What responsibilities belong in a gateway rather than in individual services? | api-gateway, architecture, operations
Why Are GraphQL N+1 Queries a Common Failure? | Advanced | API Contracts | A GraphQL query can request nested fields that resolve one item at a time, multiplying backend calls. Batching and caching are required to keep resolution efficient. | GraphQL's flexible query shape shifts performance risk from the client to the server. | How would you detect and fix N+1 resolution in a GraphQL schema? | graphql, n+1, resolution
