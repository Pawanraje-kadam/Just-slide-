# Backend Engineering
Why Does a Cache Invalidation Bug Look Like a Logic Bug? | Intermediate | Caching | Stale cached data produces results that contradict the current database, so engineers often debug business logic rather than cache keys and invalidation paths. | Caches create a second source of truth, and it is usually the less obvious one. | How would you make cache invalidation observable when it fails? | caching, invalidation, debugging
How Does a Connection Pool Become a Bottleneck? | Intermediate | Request Handling | A pool bounds concurrent database work to protect the database, but slow queries hold connections and queue new requests. Latency rises even when CPU is idle. | Pool exhaustion is a common hidden cause of cascading latency. | How would you distinguish pool waiting from slow query execution in metrics? | connection-pool, databases, latency
What Makes a Background Job Idempotent? | Intermediate | Background Jobs | Jobs can be retried after crashes or timeouts, so repeating them must not repeat side effects. Idempotency requires durable deduplication or naturally repeatable operations. | Exactly-once execution is a myth, but idempotent effects are achievable. | Where would you store deduplication state for a job that sends emails? | background-jobs, idempotency, retries
What Causes a Cache Stampede? | Advanced | Caching | When a popular key expires, many requests miss at the same moment and all recompute or fetch it, overwhelming the backing system. | Expiry policy can synchronize load in the worst possible way. | How would you make cache refreshes happen once rather than per request? | cache-stampede, caching, load
How Do Rate Limiters Protect a Service? | Beginner | Request Handling | Rate limiting caps request volume per identity or resource using token buckets, leaky buckets, or sliding windows, smoothing bursts before they reach expensive work. | It is a control against abuse and a protection for shared capacity. | What should a token bucket do when a client bursts after being idle? | rate-limiting, tokens, protection
Why Does One Database Connection Per Request Fail at Scale? | Beginner | Request Handling | Each connection consumes database memory and scheduling overhead, and connection setup is slow. At high concurrency, the database spends more time managing connections than serving queries. | Concurrency limits must be explicit; the database is a finite resource. | Why is a pool of twenty connections sometimes faster than a pool of two hundred? | databases, connections, scaling
How Should a Service Handle Partial Failures? | Advanced | Service Design | When some dependencies succeed and others fail, returning a single error can hide usable results and mislead retries. The service needs an explicit policy for degraded responses. | Partial failure is normal in distributed systems; pretending otherwise produces confusing behavior. | When is a degraded response better than a failed one? | partial-failure, resilience, apis
Why Is Request Coalescing Useful? | Intermediate | Caching | When many callers ask for the same expensive result at once, one in-flight computation can serve all of them, reducing load and latency variance. | It is a targeted fix for thundering-herd patterns without adding a full cache layer. | How would you coalesce identical requests while preserving per-caller timeouts? | coalescing, caching, thundering-herd
What Makes a Webhook Delivery System Reliable? | Advanced | Background Jobs | Webhooks need signatures, retries with backoff, ordering guarantees or explicit ordering semantics, and receiver idempotency, since the network will drop and duplicate deliveries. | Webhooks are distributed systems exposed to customers, with failure visible to their systems. | How would you let a receiver safely verify and deduplicate webhook events? | webhooks, delivery, reliability
